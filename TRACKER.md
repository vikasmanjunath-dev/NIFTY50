**Locked Phase 2 result (honestly reported):** aggregate accuracy 50.4% ± 4.4%, ROC-AUC 0.519 ± 0.044, IC +0.045 ± 0.093 across 4 folds — still no statistically robust directional edge, consistent with Phase 1 and with §1.8's realistic-expectations framing, now demonstrated with a materially richer feature set, a real ensemble, calibration and selective prediction. The cost-stressed backtest makes this concrete in economic terms: even converting raw probabilities into a simple linearly-sized position and trading it, **annualised Sharpe is negative at baseline cost (-0.48) and degrades further under 2x/5x cost stress (-1.50, -4.21)** — a real, measured instance of the blueprint's own warning that "even a 55-58% directional edge can be wiped out by costs," except here there isn't a stable edge to begin with. This is the correct, expected outcome for this stage, not a failure of the pipeline.

**A third real bug found and fixed during this work** (full detail in Work Log): isotonic calibration, fit on a calibration slice whose tail happened to be one-class-only, produced a monotonic "shelf" of *exactly* probability 1.0 for a whole region of the score range. On real validation data this produced 703 predictions at exactly 1.0 in one fold, 303 of them wrong, each contributing near-infinite log loss and inflating that fold's log loss to 1.87 (and a second fold to 3.52) — nonsensically worse than a naive 50/50 guess (0.693). Fixed by clipping every calibrated probability to [0.01, 0.99] (also independently justified: a system forecasting single-stock direction should never claim literal 100% certainty, regardless of what a finite calibration sample implies). Re-running after the fix brought every fold's log loss back into a sane 0.70–1.00 range with no other metric changing materially — confirming the fix addressed exactly the pathology and nothing else.

## Known Simplifications / Deviations (kept honest, on purpose)

1. **Data source**: using `yfinance` (Yahoo Finance) for OHLCV instead of official NSE Bhavcopy/UDiFF files. Good enough for research/backtesting at daily granularity, but lacks delivery %, and Yahoo's adjusted-close handling is not independently audited against NSE corporate-action records — flagged as a Phase-2 upgrade (§11 data sources).
6. **Live corporate-action gap (not hypothetical — actually hit)**: `TATAMOTORS.NS` and `LTIM.NS` both 404 on Yahoo as of 2026-09-18. Tata Motors demerged into separate commercial/passenger-vehicle listings (passenger entity now `TMPV.NS`); LTIMindtree's correct current ticker could not be resolved in the time available. Both are marked `ingestible=False` in `instrument_master.py` rather than silently ingested-as-empty or silently excluded — universe is **48/50** until resolved. This is the exact §13 "corporate actions" / instrument-identifier pitfall the blueprint warns about, encountered in practice within the first hour of building.
7. **No hyperparameter tuning, no calibration, no cost model applied yet in the Phase 1 baseline** — by design (§3.1's own warning about selection-adjusted statistics: tune nothing until the untuned baseline is locked and recorded). The near-zero IC / near-coin-flip accuracy reported for Phase 1 is the *expected, correct* result of that discipline, not a sign anything is broken.
8. **Environment fix applied, noted for reproducibility**: the sandbox's `scipy` was reinstalled mid-session to get `scipy.stats`, which pulled scipy 1.17 (requires numpy ≥2.0) against the pinned numpy 1.26.4, transiently breaking `sklearn` (which imports `scipy.sparse`). Fixed by pinning `scipy==1.13.1` (numpy-1.26-compatible) and avoiding a `scipy.stats` dependency in `eval/metrics.py` altogether (Spearman IC implemented directly via `pandas.Series.rank()` + `numpy.corrcoef`, ~4 lines, one fewer moving dependency). Full suite re-verified green after the fix.
9. **Macro ingestion is a deliberately separate pipeline from the equity adapter** (`data/macro.py` vs. `data/ingest.py`) — India VIX / USD-INR / Brent routinely report zero volume as their *normal* state, so reusing the equity-specific "flat OHLC + zero volume = FAIL" rule (Known Simplification / bug-fix #10 below) would misfire constantly on legitimate macro data. Kept as two small, correctly-scoped modules rather than one over-general one.
10. **Two real, non-hypothetical bugs found and fixed while closing the delivery-data gap** (full detail in Work Log): (a) NSE's official archive can return HTTP 200 with a *stale, previous-trading-day* file for a non-trading date instead of 404ing — caught via a self-consistency check against the file's own embedded date column; (b) a small number of yfinance equity bars are degenerate placeholders (open=high=low=close, zero volume) for what are, per NSE's own delivery report, genuine non-trading days — these were only WARN-flagged, letting a single bad bar silently NaN out an entire 20-day rolling window (`pandas.rolling().sum()` propagates NaN across the whole window, it does not skip it) for e.g. Chaikin Money Flow. Both are now FAIL-flagged and excluded before any feature computation. The universe was fully re-ingested after the fix; Phase 1's locked baseline report was re-run on the corrected data and re-confirmed the same near-zero-edge finding (58,924 rows post-fix vs. 59,265 before — the ~340-row difference is exactly these caught bad bars across 48 instruments).
11. **(Partly superseded 2026-11-24: `ImpactCostModel` adds spread + square-root impact vs ADV; still no latency/turnover-cap/position-sizing rows.)** **Cost model is a single blended cost+slippage bps figure** (`eval/costs.py`), charged proportionally to turnover — not the blueprint's full assumption table (§3.9: separate price/slippage/spread/latency/market-impact/turnover-cap/position-sizing rows, each with its own stress case). It is a real, honest net-of-cost number (proven to move Sharpe materially under stress, see Work Log), just a simplified one — a fuller execution simulator is a further refinement, not required to establish that costs matter here.
12. **Regime engine is rule-based, not learned** (`features/regime.py`) — trend from index MAs, volatility from VIX percentile terciles. This is explicitly one of the blueprint's two "acceptable designs" (§3.8), not a shortcut: the simpler rule-based version must prove regime-conditioning is worth having before a learned HMM/clustering model is worth the added complexity.
13. **A third real bug, found and fixed via the model/calibration layer**: isotonic regression calibration produced a monotonic "shelf" of exactly probability 1.0 for score regions where the calibration slice happened to be one-class-only, which on real validation data produced 703 absolute-certainty predictions in one fold (303 wrong), inflating that fold's log loss to 1.87 and another fold's to 3.52 — worse than a naive coin-flip (0.693). Fixed by clipping every calibrated probability to [0.01, 0.99]. Full story in the Work Log.
14. **NSE XBRL fundamentals required a real investigation before extraction, not just a fetch-and-parse**: a single filing's XBRL contains the same tag (e.g. `RevenueFromOperations`) under multiple `contextRef`s whose raw period dates can be *identical* even though one is the single-quarter figure and another is a cumulative (multi-quarter or full-year) figure — there is no way to tell them apart from the context's own dates alone. Resolved empirically before writing extraction code: fetched a company's genuinely-Consolidated filing (an independently-plausible, well-known-order-of-magnitude case) and confirmed the *smaller*-magnitude value is reliably the single-quarter figure. This "smallest value per tag" heuristic is not logically guaranteed (a loss quarter inside a cumulatively-positive year could invert it), so every extracted EPS value is cross-checked against yfinance's own (short) quarterly EPS history wherever the two overlap, and demoted to WARN rather than silently trusted when they disagree — see bug #17 below for what that cross-check actually caught.
15. **NSE's fundamentals data, in this environment, does not extend past ~Dec-2024** regardless of requested date range (tested directly with explicit `from_date`/`to_date` query parameters — the server consistently returns nothing newer). OHLCV data via yfinance extends to the present (2026-09), so there is a real, growing gap between price data and fundamentals data recency for the most recent ~1.5+ years. A merged feature row correctly reflects this as increasingly stale (but not silently wrong) carried-forward fundamentals — verified directly: Reliance's `eps_basic` in the combined feature matrix stays pinned at its Dec-2024 value all the way through the most recent ingested trading day.
16. **Insurance-sector fundamentals are an open gap**: SBILIFE and HDFCLIFE (IRDAI-regulated, a third disclosure pathway distinct from the general and banking `in-bse-fin` taxonomies both covered) returned zero filings from this API entirely. 2/48 instruments — flagged and excluded, not silently defaulted to missing-looks-like-zero.
17. **Three real, non-hypothetical bugs found and fixed while building fundamentals ingestion** (full mechanism in Work Log): (a) `NSE:M&M`'s raw `&` broke the API query string, returning zero results, until the symbol was URL-encoded; (b) every single banking stock (5/48) failed 100% because banks file under different XBRL tag names within the same taxonomy (`InterestEarned` not `RevenueFromOperations`, etc.) — added as a second candidate tag per field, tried in priority order; (c) the yfinance cross-validation check itself had a bug: it could find a matching date whose *value* was NaN and then compare against that NaN, always failing the tolerance check and reporting a false "MISMATCH" rather than "nothing to compare" — fixed with an explicit NaN check. A genuine (non-bug) mismatch that surfaced after fixing (b) and (c) — Nestlé India, ours=7.14 vs. yfinance=3.57, exactly 2x — was investigated rather than dismissed: confirmed via `yfinance`'s own split history that Nestlé India did a 2:1 stock split on 2025-08-08, *after* the Dec-2024 filing date but before "now" — yfinance retroactively restates historical EPS for splits, so its 3.57 is the post-split-adjusted figure while our 7.14 is the genuine as-filed, point-in-time-correct value. This is not an extraction error; if anything it demonstrates why extracting from primary filings rather than trusting a restated aggregator matters for point-in-time backtesting.
18. **(Partly superseded 2026-11-24: an LLM-pointwise reranker exists in `documents/rerank.py`, opt-in; trained cross-encoders (MiniLM-L6, bge-reranker-v2-m3) were added 2026-11-24 after the user approved the download; sentence-transformers/torch are now installed, and the LLM reranker `qwen3:8b` remained stronger.)** **True cross-encoder reranking is not implemented** (`documents/retrieval.py`) — hybrid retrieval stops at BM25 + dense + Reciprocal Rank Fusion. A learned reranker over the fused top-k (the blueprint's §4.6 "cross-encoder / learned reranker" row) is a further refinement; RRF already provides a principled way to combine the two signal types without needing one, so this is a real but non-blocking gap.
19. **Materiality classification needed a real, measured design correction mid-Phase-3**: an initial version exact-matched NSE's `category` field against a set curated from one company's ~6-month sample. Once the full 48-instrument, 5-year corpus was backfilled, the real taxonomy turned out to have **171 unique category strings** for a much smaller set of underlying event types (case variants, pluralisation, granular sub-types like five different flavours of "Buyback"). The exact-match version silently misclassified most of the real universe as Low. Rewritten as case-insensitive keyword matching and re-verified against the real, full category list (67% Low / 22% Medium / 11% High, with exactly the expected event types — board outcomes, M&A, results, management changes, credit ratings, dividends — populating the High tier) before being trusted.
20. **(Partly superseded 2026-11-24: sentence-transformers/torch were installed for the cross-encoder study; generation default is now `qwen3:8b`.)** **A local RAG+LLM stack was used instead of installing new heavy ML dependencies**: confirmed a local Ollama server was already running with `mxbai-embed-large` (embeddings) and several LLMs (`llama3.2:3b` used for generation) pulled and available, and used those directly rather than installing `sentence-transformers`/`torch` — avoiding a third heavy, versioned-dependency risk this session (after two real scipy/numpy ABI incidents earlier). This is a genuine, real local RAG+LLM pipeline, not a mocked stand-in — every retrieval, generation and guardrail example reported in `reports/phase3_rag_metrics.md` ran against the actual local model.
21. **Two more real bugs found via genuine end-to-end testing against the actual local LLM, not mocks** (full mechanism in Work Log): (a) `llama3.2:3b` formatted a fully-grounded, correct answer as a numbered list ("1. ... 2. ... 3. ..."), and the numeric-grounding guardrail flagged "1", "2", "3" as invented financial figures — a false positive that would have blocked a genuinely good response; fixed by excluding bare 1-2 digit integers (a documented, accepted trade-off: a genuinely wrong *small* number is no longer caught by this specific check). (b) The LLM's prompt includes each evidence item's `publication_time` (e.g. "2024-09-17..."), and a real response correctly read "2024" from that timestamp and reported it — but the guardrail only checked the raw `claim_span` text, which didn't happen to repeat the year, so it flagged a legitimately-grounded number as invented. Fixed by making the guardrail's evidence definition include everything the LLM was actually shown (publication_time and category, not just claim_span) — the general lesson: a guardrail's notion of "the evidence" must always exactly match what the model was given, or it cannot correctly judge groundedness. Re-ran the full 5-instrument example set after both fixes: 5/5 pass all guardrails (previously 4/5).
22. **The retrieval evaluation's Recall@10 (0.184) needs its denominator understood, not read as "bad"**: relevance is defined as "belongs to the same instrument" within a fixed, bounded 600-document evaluation pool (not the full 43,623-document corpus — see #23 below for why). Many instruments have well over 10 relevant documents inside that pool, so recall@10 is mathematically capped below 1.0 by construction; the Mean Reciprocal Rank (0.886) is the metric that actually reflects retrieval quality for this use case, since evidence-pack construction needs the single best-matching items, not exhaustive recall of every historical document about a company.
23. **(RESOLVED 2026-11-24 by `documents/index.py`; see Robustness additions.)** **A real, discovered architecture gap: `hybrid_retrieve` embeds its entire point-in-time-eligible candidate pool on every call** — fine for one instrument's few-hundred-document history (used successfully in the real RAG+LLM examples), but not for the full 43,000+ document, 5-year, 48-instrument corpus, where a query near the end of the history would need to embed nearly the whole corpus (tens of thousands of Ollama calls) before it could even start scoring. Discovered by watching a real run stall (CPU usage low, one long-lived connection, no progress) rather than assumed. A production system would maintain a persistent, incrementally-updated embedding index; here, the retrieval *evaluation* script works around it with a fixed, pre-embedded, stratified sample pool (standard practice for retrieval evaluation generally), but `hybrid_retrieve` itself is not yet safe to call against the full universe corpus in one pass — flagged explicitly as a Phase-4 architecture item, not silently avoided.
24. **A separate, much bigger real efficiency bug was found and fixed *before* any of the above**: the first announcements-backfill design issued one HTTP request per (symbol, ~45-day window) — about 1,900 requests, killed after 13 minutes once discovered. Investigated whether a whole-exchange endpoint existed (the same pattern that made the delivery-data backfill cheap) rather than just waiting it out: it did (omit `&symbol=` from the same API), confirmed to return *byte-for-byte identical* records to the per-symbol query when filtered client-side, and confirmed to honour date windows up to at least 365 days with no truncation (unlike the per-symbol endpoint's ~60-day cap). Rebuilt around it: the full 5-year, 48-instrument backfill dropped from an estimated ~20-25 minutes and ~1,900 requests to **13 requests and under 4 minutes**, with incremental per-window checkpointing added so a failure partway through would not discard prior progress.
2. **Universe** *(resolved 2026-11-24 for the survivorship comparison pipeline — see Phase 2.5)*: earlier phases used the *current* Nifty 50 for all history. `data/index_membership.py` + `scripts/run_survivorship_comparison.py` now measure and remove that bias. Remaining limitation: HDFC's seat (until 13 Jul 2023) has no bars (yfinance has none), so the PIT universe is honestly 49/50 for ~460 trading days; Tata Motors' pre-demerger history is Yahoo's demerger-adjusted series under `TMPV.NS`.
3. **Labels** *(refined 2026-11-24: vol-scaled barriers now implemented; see Robustness additions)*: triple-barrier implementation uses a fixed % barrier and a fixed time barrier for simplicity; volatility-scaled (ATR-based) dynamic barriers are a Phase-2 refinement.
4. **Validation**: walk-forward + purge/embargo is implemented and **CPCV is now implemented (2026-11-24)**; nested hyperparameter search (**now implemented 2026-11-24, see Robustness additions**) (§3.4, §5.2) are not yet implemented — Phase 1 uses a single walk-forward pass with fixed hyperparameters, explicitly to establish a locked, honest baseline before adding search (which introduces selection bias that must be tracked, §3.1).
